# Systematic Debugging Protocol (系统化科学调试协议)

## 核心铁律 (The Iron Law)
> **NO FIXES WITHOUT ROOT CAUSE INVESTIGATION & EVIDENCE**
> 未完成现象拆解、奥卡姆排查取证与高保真验证前，严禁提出或应用任何修复代码。
> 严禁规避问题（Workaround）。若撤销改动后根本诱因仍在，则该改动属于伪修复，必须立即停止。

---

## 阶段流程 (The 4 Phases)

### Phase 1: 现象学澄清与防锚定 (Symptom Clarification)
**目标：明确第一现场真实体感，杜绝以偏概全与错误技术归因。**

1. **执行防锚定暂停 (Anti-Anchoring Pause)**：
   - 严禁在未理解用户真实意图前直接钻入日志或代码细节。
   - 严禁向非技术用户抛出底层技术术语（如特定接口名、内部状态码）。
2. **现象学提问与行为还原**：
   - 引导用户描述**具体操作动作**（点什么、何时点）与**肉眼直观所见**（页面转圈、白屏、闪退、报错文本）。
   - 区分“用户推测的原因”与“客观发生的现象”（瓦解 XY 问题）。
   - *(详见 `references/symptom-interview-guide.md`)*。
3. **输出现象定义基线 (Symptom Baseline)**：
   - **预期行为 (Expected)** vs **实际表现 (Actual)**
   - **复现路径与频次**（必现 / 偶现 / 特定条件）
   - **影响范围**（单点 / 全局 / 特定环境）

---

### Phase 2: 问题拆解与奥卡姆排查 (Divide & Conquer)
**目标：将嵌套复杂问题打散，按概率优先级逐步二分排查，防止 LLM 注意力漂移与脑洞发散。**

1. **问题打散 (Decomposition)**：
   - 将“现象”与“可能的链路节点”解耦，绘制单向数据流或调用断点（Client → Network → Gateway → App → Storage/DB）。
   - 一次只排查一个断点，严禁同时发散多个跳步。
2. **奥卡姆剃刀排查优先级 (Occam's Priority Order)**：
   - **Priority 1 (最近变更)**：最近改了哪些代码、配置、环境变量或依赖？先做比对/回退排查。
   - **Priority 2 (当前环境与状态)**：服务是否正常存活？资源（CPU/内存/磁盘/句柄）是否耗尽？
   - **Priority 3 (依赖与外部输入)**：上游传参是否变更？下游依赖是否超时？
   - **Priority 4 (代码深层缺陷)**：仅在排除 1~3 后才深入复杂代码逻辑。
   - 🚨 **红线警示**：严禁无证据猜想极端边缘情况（如电压不稳、硬件偶发故障）。

---

### Phase 3: 单假设实验与隔离取证 (Hypothesis & Evidence)
**目标：单一变量验证，用客观数据证实或证伪。**

1. **确立单一可证伪假设 (Single Hypothesis)**：
   - 格式规范：*“我认为导致 [断点X] 异常的原因是 [Y]，因为观察到了 [证据Z]。”*
2. **最小化单变量取证**：
   - 在该断点进出口打桩（输出关键日志/指标），收集确定性数据。
   - 每次实验只改变一个变量，严禁混合多项改动。
3. **结果判定**：
   - **被证伪** → 记录证伪证据，推翻该假设，回退所有临时日志/探测代码，进入下一个断点。
   - **被证实** → 确认已直达因果链根因，方可进入 Phase 4。

---

### Phase 4: 根因修复与生产保真验证 (Fix & Production Parity)
**目标：治本修复，指标对齐生产，显式暴露测试盲区。**

1. **先造失败用例 (Failing Case First)**：
   - 先运行可复现当前异常的自动化测试或复现脚本，确认其处于 Red 状态。
2. **执行最小化根因修复**：
   - 仅做消除根因所需的最小修改，严禁夹带无关代码重构。
3. **指标真实对齐自检 (Metric Alignment Check)**：
   - *(自检问卷)*：*“我当前测试的指标是否等价于用户的真实体感？”*
   - 🚨 **严禁使用低层指标伪造高层正常**（例如：严禁用 Ping 连通代指 Web 打开正常）。
   - *(详见 `references/production-parity-and-metrics.md`)*。
4. **测试盲区声明 (Blindspot Disclosure)**：
   - 若测试环境无法 100% 模拟生产条件（如外网延迟、超大并发量、特定硬件环境），**必须在回复中显式列出“已验证项”与“未覆盖的潜在生产差异点”**。
5. **补丁链熔断机制 (Patch-Chain Circuit Breaker)**：
   - **若连续 2 次修复尝试均未通过验证，立即强制停止！**
   - **彻底回退（Revert）所有改动**，退回 Phase 1 重新审视基本假设与架构。

## 经典反模式自检清单 (Anti-Patterns Table)

| 反模式名称 | 典型错误行为 | 正确做法 |
| :--- | :--- | :--- |
| **🚨 醉汉乱撞 (Drunk Man)** | 没有明确假设，随手改几行代码碰运气看能不能跑通 | 提出单一假设，明确预期结果，单变量取证 |
| **🚨 路灯下找钥匙 (Streetlight)** | 测容易测的指标（如 Ping / 端口监听），忽视真实业务指标 | 对齐真实用户场景（如完整 HTTP 响应与渲染耗时） |
| **🚨 绕过问题 (Workaround Addiction)**| 接口慢不查慢查询，而是把超时阈值调大或降级功能 | 追问 5 个为什么，必须消除引起问题的根本原因 |
| **🚨 补丁连环坑 (Patch-Chaining)** | 第一次修复失败后在上面继续打补丁，越改越乱 | 2 次修复失败立即回退所有改动，重新审视根因 |
